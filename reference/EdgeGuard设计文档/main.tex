\section{项目介绍}

\subsection{项目背景}

智能座舱正成为汽车差异化竞争的核心战场。特斯拉通过语音+触屏实现了基本的无按钮交互，蔚来NOP+引入了NOMI拟人化语音助手，华为鸿蒙座舱集成了多模态感知能力。然而，这些方案的AI决策高度依赖云端——一旦进入隧道或偏远地区，语音助手和智能推荐便大幅降级。同时，驾驶员状态监测（DMS）在多数量产车型中仍停留在简单的PERCLOS阈值判断阶段，误报率高且缺乏趋势预测能力。

在学术研究层面，多模态融合感知已有多条技术路线：基于规则的专家系统（如传统DMS）、基于深度学习的端到端模型、以及基于大语言模型的Agent编排。Google的MediaPipe提供了开源的面部/手势关键点检测能力，Meta的FAISS使本地向量检索成为可能，LangChain/LangGraph生态则为多Agent编排提供了框架支持。这些开源工具的成熟，使得在消费级硬件上构建多模态车载交互原型成为可行。

本项目为南开大学计算机学院"大模型应用开发实训"课程的团队项目。课程要求每组选择一个应用场景，利用大语言模型和相关AI技术完成从设计到部署的完整闭环。我们选择车载智能座舱场景，因为该场景天然要求多模态输入融合、边缘-云端混合架构和实时安全保障，能够充分体现大模型在复杂工程场景中的落地价值。

具体而言，现有车载交互系统存在以下不足：
\begin{enumerate}
    \item \textbf{云端依赖过重}：AI决策依赖云端大模型，断网时系统失去智能能力。典型场景：隧道中语音助手无响应、偏远地区导航推荐失效；
    \item \textbf{交互模态单一}：语音或触屏为主，缺乏多模态融合感知。手势控制和眼动追踪在量产车型中应用有限；
    \item \textbf{安全功能滞后}：疲劳检测多为硬阈值判断（如连续闭眼>2秒触发告警），误报率高，缺乏基于趋势的预测能力；
    \item \textbf{知识能力有限}：仅支持预设指令集，无法回答"仪表盘亮了黄色发动机图标是什么意思"等开放性问题。
\end{enumerate}

针对上述问题，本项目设计并实现了EdgeGuard——一套面向边缘侧的多模态AI车载交互原型系统。

\subsection{项目目标}

本项目旨在构建一个面向智能座舱场景的多模态AI交互原型系统，核心目标包括：

\begin{enumerate}

    \item \textbf{多模态融合感知}：集成眼动、手势、语音、环境四模态数据采集与融合分析；
    \item \textbf{多Agent协作决策}：基于LangGraph编排七个专业Agent（安全/意图/交互/诊断/分析/推荐/审计），实现三层拓扑并行分析与VETO安全短路；
    \item \textbf{RAG车辆知识库}：基于FAISS向量检索的车辆知识问答系统，支持自然语言查询；
    \item \textbf{车载中控可视化}：Vue3中控大屏实时展示驾驶状态、AI决策链路和环境信息。
\end{enumerate}

\subsection{非目标}

明确以下非目标，有助于读者理解后续设计决策的边界：

\begin{itemize}
    \item \textbf{非真实车载硬件集成}：本项目为实训原型，不对接真实车辆CAN总线、ECU或OBD接口。感知数据来自USB摄像头和麦克风，控制指令仅在前端模拟呈现，不执行实际车辆控制；
    \item \textbf{非高可用生产系统}：系统设计面向单机原型演示，不考虑多副本部署、负载均衡和异地容灾。云端部署为功能验证用途，SLA目标仅为"尽力可用"；
    \item \textbf{非实时操作系统}：感知层延迟目标为<50ms，但运行在通用操作系统（Windows/Linux）上，不保证硬实时性。疲劳检测为趋势预测而非紧急碰撞干预；
    \item \textbf{非自研大模型}：系统不训练或微调自有模型，所有LLM能力通过DeepSeek API外部调用获得。本地推理仅限于MediaPipe和TFLite等预训练轻量模型。
\end{itemize}

\subsection{项目范围}

本系统为实训课程的原型项目，聚焦核心功能链路验证，不涉及真实车辆硬件集成。主要覆盖以下功能范围：

\begin{itemize}
    \item \textbf{感知层}：MediaPipe面部468关键点追踪、虹膜定位、PnP头部姿态解算、手势关键点分类、Whisper语音转写；
    \item \textbf{决策层}：LangGraph六Agent编排、边缘-云端混合路由、本地决策引擎（37条关键词）；
    \item \textbf{交互层}：Vue3中控大屏、WebSocket实时推送、TTS语音播报、AI主动观察提醒；
    \item \textbf{知识层}：FAISS向量检索+RAG生成、车辆故障码知识库、Offline模板库兜底。
\end{itemize}

\subsection{技术选型理由}

\subsubsection{为什么选FastAPI而非Flask？}

FastAPI具有原生异步支持（async/await），适合同时处理摄像头推流、WebSocket连接和HTTP请求的并发场景。其自动生成的OpenAPI文档（/docs端点）方便前后端联调。EdgeGuard后端包含44个REST端点（main.py 35个 + routes/music.py 7个 + routes/settings.py 2个）和5个WebSocket通道，FastAPI的异步特性能够有效支撑这些并发需求。

\subsubsection{为什么选DeepSeek而非GPT/Claude？}

DeepSeek Chat API在国内可直接访问，无需代理；提供免费额度，适合学生实训项目；兼容OpenAI API格式，切换成本低。系统设计了\texttt{LLM\_PROVIDER}环境变量机制，修改配置即可切换到OpenAI或Anthropic。

\subsubsection{为什么需要LangGraph编排？}

单一Agent无法有效处理多模态并发输入。LangGraph的StateGraph支持条件路由、并行执行和优先级短路——SafetyAgent检测到危险状态时可通过VETO机制立即跳过后续所有Agent直接告警。系统采用三层拓扑编排七个Agent：SafetyAgent（串行，VETO短路）$\rightarrow$ IntentionAgent（串行，意图路由）$\rightarrow$ 四个执行Agent并行（Interaction/Diagnose/Analyze/Recommend）$\rightarrow$ EvidenceAuditAgent（串行，真实性审计）$\rightarrow$ Aggregate（聚合输出）。所有Agent继承自BaseScaffoldAgent基类，通过Pydantic模型实现入参/出参自动校验，统一入口\texttt{run()}保证类型安全。EvidenceAuditAgent在聚合前对全部Agent输出进行四项审计检查（引用真实性/矛盾检测/假设误报/数字溯源），严重问题（severity=error）时阻断不安全回复。

\subsubsection{为什么核心安全功能在本地？}

行车安全场景对延迟要求极高（<50ms），且网络环境不稳定（隧道、偏远地区）。将眼动追踪、疲劳检测、手势识别部署在本地推理，既保证低延迟，又确保断网时核心安全功能不中断。

\subsection{核心数据流}

系统主循环的数据流如下：摄像头采集帧 → MediaPipe面部追踪（468点）→ 虹膜定位+EAR计算+头部姿态 → 手势检测（跳帧采样，每N帧一次）→ 本地决策引擎综合判断 → 告警分级 → WebSocket推送前端 + HTTP响应携带状态数据。同时，语音输入通过Whisper转写 → 关键词匹配（本地优先）或DeepSeek语义理解（复杂语句） → 意图分类 → 执行对应操作。

\section{可行性分析}

\subsection{技术可行性}

本项目所选技术栈均为成熟的开源方案，无需购买商业授权：

\begin{enumerate}
    \item \textbf{视觉感知}：MediaPipe是Google开源的跨平台机器学习框架，Face Landmarker提供468个面部关键点，其Python SDK已稳定迭代至0.10.x版本；OpenCV的DShow后端在Windows平台有成熟驱动支持；
    \item \textbf{大模型调用}：DeepSeek提供兼容OpenAI格式的REST API，Python SDK封装完善，调用方式与ChatGPT一致，学习成本低；
    \item \textbf{Agent框架}：LangGraph是LangChain生态下的状态图编排框架，文档完善，社区活跃，ReAct模式的StateGraph有官方示例可参考；
    \item \textbf{向量检索}：FAISS是Meta开源的向量检索库，支持十亿级向量毫秒级检索，本项目的车辆知识库仅需千级向量，性能绰绰有余；
    \item \textbf{Web框架}：FastAPI是目前Python生态最主流的异步Web框架，性能接近Node.js，且自带交互式API文档；
    \item \textbf{前端框架}：Vue3+TailwindCSS是当前前端主流技术组合，组件生态丰富，响应式布局成熟。
\end{enumerate}

所有技术组件均经过工业级验证，集成风险可控。

\subsection{经济可行性}

本项目为零成本开发：

\begin{itemize}

\subsection{系统流程设计}

系统主流程分为三个阶段：启动初始化、运行时主循环、会话结束。

\subsubsection{启动初始化}

后端启动 → 加载.env环境变量 → 初始化DeepSeek客户端 → 初始化EdgeCloudRouter（网络检测）→ 初始化FAISS索引（首次启动自动构建）→ 初始化数据库表 → 启动uvicorn → 前端加载中控大屏 → WebSocket连接建立。

\subsubsection{运行时主循环}

摄像头采集帧 → MediaPipe面部追踪（468点+虹膜+EAR+头部姿态）→ 手势检测（跳帧采样）→ 本地决策引擎综合判断 → 告警防抖（3帧2票+6秒冷却）→ 结果推送（HTTP状态+WebSocket广播）。语音输入异步处理：Whisper转写 → 关键词匹配（本地优先）→ DeepSeek语义理解（复杂语句）→ Agent编排 → 执行动作。

\subsubsection{Agent编排流程}

路由分类器（route\_classifier.py）根据驾驶状态和用户输入选择执行路径 → SafetyAgent串行执行传感器风险评估（VETO权：危险状态短路到Aggregate直接告警）→ IntentionAgent串行分解意图并路由 → 四个执行Agent并行处理（Interaction/Diagnose/Analyze/Recommend）→ EvidenceAuditAgent串行审计全部输出（引用真实性/矛盾检测/假设误报/数字溯源，severity=error时阻断不安全回复）→ Aggregate聚合生成最终回复 → 记录日志。当route\_classifier检测到危险驾驶状态时，即使前端发送route='quick'，安全前置门也强制将其升级为route='multi'，确保必定经过SafetyAgent审查。

\section{详细设计}

\subsection{视觉感知模块}

\subsubsection{面部追踪（face\_tracker.py）}

面部追踪模块基于MediaPipe Face Landmarker提取468个面部关键点，实现以下核心功能：

\textbf{虹膜定位}：利用MediaPipe预训练的虹膜关键点模型（Iris Landmarker），从468点中提取左右眼虹膜中心坐标。虹膜位置相对于眼角的偏移量用于计算视线方向：水平方向$\pm$0.22阈值、垂直方向$\pm$0.15阈值，超出阈值判定为视线偏离。

\textbf{眼睑闭合度（EAR）}：基于眼睑关键点计算Eye Aspect Ratio，公式为：

$$EAR = \frac{||p_2 - p_6|| + ||p_3 - p_5||}{2||p_1 - p_4||}$$

其中$p_1$至$p_6$为眼周6个关键点的坐标。前60帧中位数采样作为个人基线，后续帧与基线对比计算PERCLOS（闭眼时间比例）。

\textbf{头部姿态估计}：采用PnP几何解算方法，将468个3D面部模型点与2D图像关键点匹配，通过solvePnP求解旋转向量，输出pitch、yaw、roll三个欧拉角。yaw角$\pm$10°、pitch角$\pm$8°作为正常范围阈值（基于Haar人脸框偏移量估算）。

\textbf{防抖与分级机制}：
\begin{itemize}
    \item \textbf{8帧平滑窗口}：视线方向取最近8帧，在最近5帧中至少3票一致才确认状态变化，消除单帧抖动；
    \item \textbf{3级告警阈值}：2秒→mild提醒、3秒→moderate警告、5秒→severe严重告警，五类告警（多人/离位/疲劳/头部偏离/视线偏离）统一采用此三级阈值；
    \item \textbf{跳帧采样}：手势检测每3帧执行一次，其余帧复用上次结果，有效降低GPU负载约60\%。
\end{itemize}

\textbf{性能优化}：采用跳帧采样策略，每隔N帧（默认3帧）执行一次手势检测，其余帧复用上次检测结果，有效降低GPU负载约60\%。

\subsubsection{摄像头引擎（camera.py）}

摄像头引擎是感知层的中枢模块，封装完整的采集管线：

\begin{itemize}
    \item \textbf{驱动适配}：优先尝试DShow后端（cv2.CAP\_DSHOW），解决Windows默认MSMF后端取帧失败的问题；
    \item \textbf{主循环}：每帧 → 面部追踪 → 手势检测（跳帧）→ 本地决策引擎 → HUD叠加 → JPEG推流 → 状态推送；
    \item \textbf{HUD叠加}：实时绘制视线方向箭头、手势名称、告警等级文字到画面；
    \item \textbf{双通道推送}：HTTP响应头携带结构化状态数据（视线/手势/告警）+ WebSocket广播实时事件；
    \item \textbf{干跑模式}：设置环境变量\texttt{CAMERA\_ENABLED=0}跳过摄像头初始化，用模拟数据测试决策链路；
    \item \textbf{异常处理}：摄像头被占用→自动释放重试，模型文件缺失→优雅降级，摄像头断开→自动清理资源。
\end{itemize}

\subsection{AI决策模块}

\subsubsection{本地决策引擎（local\_decision\_engine.py）}

设计理念：高频指令本地处理（毫秒级），复杂语义才走大模型（秒级）。核心实现包括：

\textbf{关键词匹配表}：37条日常口语表达，按功能分类组织为6大类——空调控制、音乐播放、导航请求、车窗灯光控制、安全确认语句、知识查询。

\textbf{匹配策略}：最长匹配优先。例如"导航去天安门"匹配"导航去"而非"去"，确保匹配结果是最具体的意图。

\textbf{手势→指令映射}：GESTURE\_MAP汇聚TFLite 8类标签与几何分类器16种手势（共26条映射），输出统一action\_code，识别结果通过摄像头引擎实时推送前端。

\textbf{眼动分析}：三级严重度分级（mild提醒/moderate警告/dangerous告警），依据视线偏离持续时长逐级触发，配合防抖+冷却机制。

\subsection{Agent编排模块}

\subsubsection{BaseScaffoldAgent基类（base\_agent.py）}

所有Agent继承自BaseScaffoldAgent泛型基类，采用TradePilot风格的脚手架架构。每个子类需声明三个组件：

\begin{itemize}
    \item \textbf{input\_model}：入参Pydantic类型，定义Agent接受的传感器/上下文数据结构；
    \item \textbf{output\_model}：出参Pydantic类型，继承ScaffoldAgentOutput基类（含status/conclusions/evidence\_ids/errors等元数据字段）；
    \item \textbf{\_run\_impl()}：子类实现的具体推理逻辑。
\end{itemize}

基类通过LCEL链（RunnableSequence）编排三步流水线：\texttt{\_validate\_input}（dict自动转Pydantic实例）$\rightarrow$ \texttt{\_run\_impl}（子类推理）$\rightarrow$ \texttt{\_validate\_output}（dict自动转Pydantic实例）。对外统一入口\texttt{run(context)}接收InputT或dict，返回已校验的OutputT，保证类型安全。

所有Agent的Input/Output模型定义在\texttt{schemas.py}中，按Agent分组组织。ScaffoldAgentOutput基类统一携带执行元数据（model\_call\_count、parse\_retry\_count、token\_usage），支持全链路追踪。

\subsubsection{模型工厂（model\_factory.py）}

模型工厂按Agent角色创建LLM实例，通过AGENT\_MODEL字典映射Agent名到模型工厂函数：

\begin{itemize}
    \item \textbf{快速模型}（create\_fast\_model）：豆包Lite优先，降级DeepSeek Chat。用于SafetyAgent/IntentionAgent/InteractionAgent/EvidenceAuditAgent——这些Agent对延迟敏感且推理复杂度低；
    \item \textbf{推理模型}（create\_reasoning\_model）：DeepSeek Reasoner优先，降级豆包Lite。用于DiagnoseAgent/AnalyzeAgent/RecommendAgent——这些Agent需要深度推理能力。
\end{itemize}

模型参数（temperature/timeout/max\_retries/max\_tokens）从环境变量读取，支持运行时调整。\texttt{structured\_output.py}中的\texttt{invoke\_structured()}函数实现六步LLM$\rightarrow$Pydantic校验链：prompt填充 $\rightarrow$ model调用 $\rightarrow$ decode（去markdown+提取JSON）$\rightarrow$ serialize（json.dumps）$\rightarrow$ PydanticOutputParser校验 $\rightarrow$ 失败重试（最多3次）。

\subsubsection{路由分类器（route\_classifier.py）}

路由分类器根据用户输入文本和驾驶状态自动选择最优执行路径，分类规则按优先级从高到低：

\begin{enumerate}
    \item \textbf{危险驾驶状态} $\rightarrow$ multi（走SafetyAgent VETO短路）。\texttt{is\_dangerous\_driver\_state()}函数统一判断多字段：severity为dangerous/severe、fatigue\_level为danger、fatigue\_score$\geq$80、perclos$\geq$0.5；
    \item \textbf{状态查询类}（如"在播什么歌"）$\rightarrow$ react，防止被误判为播放指令；
    \item \textbf{知识查询类}（如"什么意思""怎么办"）$\rightarrow$ react，需要LLM推理；
    \item \textbf{多意图连接词}（并/同时/还有/然后等）$\rightarrow$ multi，多Agent编排；
    \item \textbf{快速指令关键词}（空调/音乐/车窗等18条正则）$\rightarrow$ quick，跳过LLM；
    \item \textbf{默认} $\rightarrow$ react，ReAct推理。
\end{enumerate}

\textbf{安全前置门}：在\texttt{backend/main.py}的\texttt{\_run\_unified\_agent\_sync()}中，即使前端显式发送route='quick'，只要\texttt{is\_dangerous\_driver\_state()}返回True，也强制升级为route='multi'，确保危险状态必定经过SafetyAgent审查。此设计保证了安全审计的不可绕过性。

\subsubsection{LangGraph三层拓扑编排}

系统将AI决策拆分为7个专业Agent，采用LangGraph StateGraph实现三层拓扑编排（\texttt{multi\_agent\_graph.py}）。这一拆分的取舍在于：7个Agent增加了编排复杂度和状态管理成本，但换来了四个关键收益——SafetyAgent可独立短路告警（VETO权，不等待其他Agent）、各执行Agent可并行降低端到端延迟、EvidenceAuditAgent在聚合前拦截不安全回复、单个Agent的Prompt可针对其领域精简。

三层拓扑结构如下：

\begin{enumerate}
    \item \textbf{第一层（串行）}：SafetyAgent $\rightarrow$ IntentionAgent。SafetyAgent先执行传感器风险评估，若判定dangerous则VETO短路到Aggregate直接告警；否则IntentionAgent分解用户意图并路由到下游Agent；
    \item \textbf{第二层（并行）}：IntentionAgent fan-out到四个执行Agent——InteractionAgent/DiagnoseAgent/AnalyzeAgent/RecommendAgent并行处理，各Agent仅处理属于自己意图类别的任务（通过\texttt{agents\_to\_run}列表过滤）；
    \item \textbf{第三层（串行）}：四Agent fan-in到EvidenceAuditAgent $\rightarrow$ Aggregate。EvidenceAuditAgent审计全部Agent输出，Aggregate节点根据VETO/澄清/审计阻断/正常四种情况生成最终回复。
\end{enumerate}

LangGraph不可用时自动降级为\texttt{\_process\_sequential()}顺序执行，保持功能完整性。状态在TypedDict中流转，累加字段（agents\_used/all\_evidence/errors）使用operator.add reducer合并。

\subsubsection{SafetyAgent}

负责驾驶安全评估，分析眼动数据和头部姿态数据，输出四级风险等级（RiskLevel枚举）：

\begin{itemize}
    \item \textbf{normal}：所有指标正常，视线在前方，眨眼频率稳定；
    \item \textbf{attn\_declining}：眨眼频率上升或头部有小幅度偏转，提示注意；
    \item \textbf{distracted}：视线持续偏离>3秒或头部偏转角度>10°，警告+限制娱乐功能；
    \item \textbf{dangerous}：严重分心+高疲劳度，紧急告警，触发VETO短路。
\end{itemize}

SafetyAgent接收SafetyAgentInput（gaze/head\_pitch/head\_yaw/head\_roll/perclos/blink\_rate/fatigue\_score/num\_faces），输出SafetyOutput（risk\_level/risk\_score/should\_veto/recommendation）。当\texttt{should\_veto=True}或\texttt{risk\_level=dangerous}时，路由函数\texttt{\_route\_after\_safety()}将执行流直接导向Aggregate节点，跳过IntentionAgent和全部执行Agent。

传感器数据映射策略：gaze/head\_pitch/head\_yaw/head\_roll使用结构化字段传入（canonical），eye\_frames传入raw\_data（PERCLOS计算需要原始帧序列），避免前端相机的小幅抖动误触发heavy\_head$\rightarrow$distracted误判。

\subsubsection{InteractionAgent}

处理手势和语音输入，进行意图解析。工作流程：接收感知数据 → 查询Intent分类表 → 简单指令返回action\_code（本地处理）→ 复杂语义调用DeepSeek LLM → 返回结构化意图（intent类型+参数+对应action\_code）。

证据审计Agent（agents/evidence\_audit.py），在所有执行Agent完成后、Aggregate聚合前串行运行，对全部Agent输出执行四项审计检查：

\subsubsection{AnalyzeAgent}

驾驶行为分析Agent，接收驾驶会话数据（时长、分心次数、严重告警次数、注意力评分、平均视线方向），调用DeepSeek LLM生成结构化驾驶报告，输出总结和建议两部分。该Agent同时支持实时主动观察模式——根据视线模式和注意力评分判断是否需要主动提醒驾驶员。

\subsubsection{DiagnoseAgent}

车辆故障诊断Agent，结合RAG知识库和DeepSeek LLM，对用户描述的车辆异常症状进行诊断分析。通过FAISS向量检索匹配车辆手册中的相关故障码和解决方案，再由LLM生成通俗易懂的诊断建议和处置方案。

\subsubsection{RecommendAgent}

行程推荐Agent，负责景点搜索和行程规划。整合小红书景点数据（cookie爬虫）与高德POI数据（LLM增强），支持用户指定景点搜索、子景点合并、多约束行程规划（天数/偏好/避开城市/途经点）。规划结果包含时间轴（参观/用餐/交通/休息）和预算计算（门票/餐饮/交通），通过结构化推送同步到前端TripPlanView面板。

\subsection{知识服务模块}

\subsubsection{RAG车辆知识库（vehicle\_knowledge\_base.py）}

基于FAISS+Sentence-Transformers的本地检索增强生成系统：

\textbf{文档处理}：将\texttt{vehicle\_manual.txt}（包含车辆使用说明、常见故障码、仪表盘指示灯含义等）以空行（\texttt{\textbackslash n\textbackslash n}）为分隔符按段落分割，过滤掉长度小于10字符的无效段落。

\textbf{向量化与索引}：使用Sentence-Transformers的paraphrase-multilingual-MiniLM模型将文本块编码为384维向量，存入FAISS IndexFlatIP（内积相似度索引）。

\textbf{检索流程}：用户提问 → 向量编码 → FAISS检索Top-K（默认K=3）→ 拼接上下文 → DeepSeek LLM生成回答。

\subsubsection{Agent记忆系统（memory.py）}

三层记忆架构：

\begin{itemize}
    \item \textbf{工作记忆（WorkingMemory）}：当前会话的最近N次交互历史，存储在内存中，会话结束后清空。同时缓存最近一次行程规划参数（last\_trip\_params）和工具结果摘要（last\_tool\_results），支持多轮对话中引用上轮结果；
    \item \textbf{长期记忆（LongTermMemory）}：SQLite持久化的对话摘要和用户偏好，跨会话保留。偏好支持like/dislike类型区分，并带有指数衰减权重；
    \item \textbf{偏好记忆}：用户显式设置（如"我喜欢的温度是22度"），通过user\_preferences表存储，支持自动从用户文本中提取偏好；
    \item \textbf{语义地点记忆}：用户设置的常用地点（如"我家在XX路"），通过saved\_locations表持久化，导航时自动识别"回家"等语义指令。
\end{itemize}

\section{其他方案}

在设计过程中，团队对若干关键技术决策考察了替代方案。本节记录主要取舍点及最终选择原因，避免读者带着疑问阅读全文。

\subsection{单LLM调用 vs.\ 多Agent编排}

\textbf{替代方案}：将所有感知数据和用户指令一次性发送给DeepSeek，由LLM直接输出最终决策。实现简单，无需LangGraph编排。

\textbf{未选原因}：单次LLM调用的延迟为1.5--4秒，无法满足SafetyAgent的<50ms响应要求。更重要的是，单LLM调用无法实现VETO短路——当SafetyAgent检测到危险状态时，应立即告警而非等待其他分析完成；也无法在输出前进行EvidenceAuditAgent的真实性审计。多Agent编排虽然增加了系统复杂度，但换来了并行执行、安全VETO短路和证据审计三重保障。

\subsection{dlib vs.\ MediaPipe面部追踪}

\textbf{替代方案}：使用dlib的68点面部关键点检测器，配合FG2018虹膜模型。dlib在学术界广泛使用，相关论文和实现丰富。

\textbf{未选原因}：dlib在Python 3.13环境下无预编译wheel包，从源码编译需要CMake和Boost依赖，编译耗时且容易失败。MediaPipe提供468个面部关键点（远多于dlib的68点），且原生支持虹膜定位，无需额外模型。此外，MediaPipe的Python SDK在0.10.x版本已稳定支持Python 3.13，安装即用。

\subsection{PostgreSQL vs.\ SQLite}

\textbf{替代方案}：使用PostgreSQL作为主数据库，支持更完善的并发控制、事务隔离和全文检索。

\textbf{未选原因}：本项目的数据规模为千级记录（驾驶会话、告警、交互日志），读写频率低（单用户原型），无并发写入需求。SQLite的零配置特性使部署仅需复制文件，而PostgreSQL需要独立的数据库服务进程。对于Agent记忆库，SQLite的WAL模式已足够支持读写并发。选择SQLite的代价是缺乏内置的全文检索和网络访问能力，但本项目通过FAISS向量检索和FastAPI REST接口分别弥补了这两点。

\subsection{SSE vs.\ WebSocket实时通信}

\textbf{替代方案}：使用Server-Sent Events（SSE）推送实时数据。SSE基于HTTP，实现更简单，自动重连，无需处理连接升级。

\textbf{未选原因}：系统需要双向通信——前端不仅接收推送（驾驶状态、告警），还需要向后端发送控制指令（语音输入、手势确认）。SSE仅支持服务端到客户端的单向推送，若使用SSE则需要额外维护一条HTTP POST通道，增加复杂度。WebSocket的单连接双向通道更契合本场景，且FastAPI原生支持WebSocket路由。代价是WebSocket需要手动实现重连逻辑（当前为5秒间隔自动重连）。

%=============================================
\section{系统鲁棒性设计}

\subsection{异常统一兜底}

SafeExecutor（safe\_executor.py）为所有Agent调用和模型加载提供统一的异常兜底：

\begin{itemize}
    \item \textbf{safe\_call()}：通用函数调用包装，支持超时、重试、默认值，异常返回default而非抛出；
    \item \textbf{safe\_agent\_call()}：Agent调用专用包装，超时8秒，失败返回带错误信息的默认响应；
    \item \textbf{safe\_model\_load()}：模型文件加载包装，文件缺失时返回None而非崩溃，上层自动降级。
\end{itemize}

Agent模块调用通过safe\_executor（safe\_executor.py）统一异常兜底，单个模块故障不会导致整个后端500错误。

\subsection{告警防抖与冷却}

为防止同一事件反复触发告警造成用户体验下降，系统实现了多层级防抖机制：

\begin{itemize}
    \item \textbf{帧级防抖}：同一风险等级需连续3帧中出现2帧以上才确认触发；
    \item \textbf{语音冷却}：两次TTS语音播报之间至少间隔6秒，避免连续告警语音重叠；
    \item \textbf{告警去重}：同一类型的告警在冷却期内不重复记录数据库，不重复推送前端。
\end{itemize}

\section{交叉关注点}

\subsection{安全与隐私}

作为车载系统，安全性设计为必需项。本系统虽为原型，仍从以下维度进行了考量：

\begin{itemize}
    \item \textbf{安全前置门（Safety Override）}：在\texttt{main.py}的\texttt{\_run\_unified\_agent\_sync()}中，即使前端显式发送route='quick'，只要\texttt{is\_dangerous\_driver\_state()}检测到危险驾驶状态（severity=severe/dangerous、fatigue\_score$\geq$80、perclos$\geq$0.5等），也强制升级为route='multi'，确保危险状态必定经过SafetyAgent VETO审查。此设计保证了安全审计的不可绕过性；
    \item \textbf{VETO短路机制}：SafetyAgent在LangGraph三层拓扑中串行执行于所有Agent之前。当判定risk\_level=dangerous时，通过条件路由函数\texttt{\_route\_after\_safety()}直接跳转到Aggregate节点告警，跳过IntentionAgent和全部执行Agent，实现<50ms安全响应；
    \item \textbf{审计阻断（Audit Blocking）}：EvidenceAuditAgent在Aggregate聚合前串行审计全部Agent输出。当检测到hallucinated\_ref（引用不存在的证据）等error级问题时，audit\_status=blocking，Aggregate节点拦截不安全回复并返回安全提示，防止幻觉内容到达用户；
    \item \textbf{安全门控（Safety Gate）}：所有Agent工具调用经过safety\_gate.py白名单过滤。当SafetyAgent判定风险等级为dangerous时，娱乐类工具（音乐播放、空调调节）被屏蔽，仅允许安全告警和紧急联系工具执行；
    \item \textbf{意图安全守卫}：IntentGuard对用户指令进行二次校验，防止通过语音注入执行危险操作（如"关闭所有传感器"）；
    \item \textbf{隐私考量}：面部图像和语音数据均在本地处理，不上传原始生物特征数据至云端。仅将提取后的结构化特征（EAR值、手势标签、转写文本）发送给DeepSeek API。用户偏好和语义地点存储在本地SQLite，不与第三方共享。
\end{itemize}

\textbf{已知局限}：系统未实现用户身份认证（无登录机制），API端点对同一网络内所有设备开放。这在原型阶段可接受，但量产部署需增加Token认证和端到端加密。

\subsection{可扩展性}

系统在以下维度预留了扩展空间：

\begin{itemize}
    \item \textbf{Agent扩展}：LangGraph的StateGraph支持热插拔新Agent。新增Agent只需实现analyze()接口并注册到Orchestrator，无需修改现有Agent代码；
    \item \textbf{工具扩展}：Agent工具系统基于function calling，新增工具只需在tools.py中注册函数并添加prompt描述；
    \item \textbf{LLM切换}：通过\texttt{LLM\_PROVIDER}环境变量可在DeepSeek、OpenAI、Anthropic之间切换，deepseek\_client.py封装了统一调用接口。
\end{itemize}

\textbf{扩展瓶颈}：当前架构为单进程单实例，无法横向扩展。SQLite的并发写入能力有限（虽然WAL模式支持并发读），若需多客户端同时使用，需迁移至PostgreSQL并引入消息队列。

\subsection{数据完整性}

\begin{itemize}
    \item \textbf{事务保障}：SQLite默认开启ACID事务，驾驶会话和告警记录的写入具有原子性。Agent记忆库的偏好更新和语义地点保存均通过显式事务提交；
    \item \textbf{备份策略}：云端部署创建了\texttt{db\_backup.tar.gz}数据库备份文件，包含三个SQLite数据库的完整快照。本地开发环境通过Git版本控制管理代码，数据库文件在.gitignore中排除；
    \item \textbf{数据一致性}：Agent工作记忆（内存）与长期记忆（SQLite）之间可能存在短暂不一致——会话进行中工作记忆尚未持久化时若进程崩溃，最近N条交互将丢失。这是内存-磁盘分离架构的固有代价，通过会话结束时统一持久化缓解。
\end{itemize}

\subsection{延迟}

系统的延迟分三个层级，各有不同的应对策略：

\begin{itemize}
    \item \textbf{感知层（<50ms）}：MediaPipe CPU推理+跳帧采样，满足实时性要求。手势检测每3帧执行一次，非检测帧复用结果，延迟降至<1ms；
    \item \textbf{本地决策层（<5ms）}：关键词匹配+规则判断，无网络IO。语音识别的Whisper转写延迟<2秒，通过异步处理不阻塞主循环；
    \item \textbf{云端LLM层（1.5--4s）}：DeepSeek API网络延迟。系统设计了60秒超时+5秒双重检测机制，超时后降级为本地规则兜底。plan\_trip等复杂工具可能耗时35秒，已将前端超时调整为60秒以覆盖。
\end{itemize}

\subsubsection{精简依赖策略}

云服务器无摄像头和麦克风硬件，因此创建了\texttt{requirements-server.txt}精简依赖文件，排除了以下重量级包：

\begin{itemize}
    \item \textbf{opencv-python}、\textbf{mediapipe}、\textbf{tensorflow}：视觉感知相关，服务器无摄像头硬件；
    \item \textbf{openai-whisper}、\textbf{sounddevice}、\textbf{webrtcvad}：语音采集相关，服务器无麦克风硬件；
    \item \textbf{faiss-cpu}、\textbf{sentence-transformers}：向量检索相关，云端查询走LLM路径无需本地Embedding。
\end{itemize}

后端代码中已内置降级逻辑：\texttt{lifespan()}启动时通过\texttt{try/except ImportError}跳过摄像头引擎初始化，\texttt{.env}中\texttt{CAMERA\_ENABLED=0}关闭摄像头功能，系统在无感知硬件的环境下正常运行所有API和Agent功能。

\subsubsection{systemd服务配置}

三个服务均通过systemd管理，配置文件位于\texttt{/etc/systemd/system/}目录：

\begin{itemize}
    \item \texttt{edgeguard-backend.service}：\texttt{ExecStart=/root/code/group05/venv/bin/python -m uvicorn main:app -{}-host 0.0.0.0 -{}-port 8000}，\texttt{Restart=always}，\texttt{PYTHONPATH}包含项目根目录和backend目录；
    \item \texttt{edgeguard-music.service}：\texttt{ExecStart=/usr/local/bin/node app.js}，工作目录为音乐API目录；
    \item \texttt{nginx.service}：系统自带，监听8055端口，配置文件位于\texttt{/etc/nginx/sites-available/edgeguard}。
\end{itemize}

所有服务通过\texttt{systemctl enable}设为开机自启，进程异常退出后5秒内自动重启。日志输出至\texttt{/tmp/edgeguard-backend.log}和\texttt{/tmp/edgeguard-music.log}。

\subsubsection{Nginx反向代理配置}

Nginx配置文件（\texttt{/etc/nginx/sites-available/edgeguard}）的核心内容：

\begin{verbatim}
server {
    listen 8055;
    server_name _;
    client_max_body_size 50M;

    location /ws/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 86400;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_read_timeout 120s;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
    }
}
\end{verbatim}

\texttt{/ws/}路径配置了WebSocket协议升级（\texttt{Upgrade}和\texttt{Connection}头部），\texttt{proxy\_read\_timeout}设为86400秒以支持长连接。\texttt{/api/}路径的超时设为120秒，覆盖\texttt{plan\_trip}等耗时工具的执行时间。

\section{未来计划}

本项目完成了多模态车载交互的核心链路验证，但距离可量产的车载系统仍有差距。以下未来计划按优先级排列，帮助读者理解当前设计的定位和演进方向。

\subsection{短期：模型轻量化与端侧部署}

当前Whisper模型（约1.5GB）在本地推理时首次加载耗时较长。计划引入Whisper.cpp或faster-whisper进行量化加速，将模型体积压缩至200MB以内，加载时间降至3秒以下。同时探索将DeepSeek的常用意图分类和驾驶建议生成蒸馏到本地小模型（如Qwen-1.8B），进一步降低对云端API的延迟依赖。

\subsection{中期：真实硬件对接与多用户支持}

当前系统的感知数据来自USB摄像头，控制指令仅在前端模拟。下一步计划对接树莓派+摄像头模组的嵌入式平台，验证在ARM架构下的推理性能。在数据层面，计划从SQLite迁移至PostgreSQL并引入用户认证机制，支持多驾驶员独立配置偏好和语义地点。

\subsection{长期：V2X融合与个性化驾驶画像}

远期愿景是将系统接入车联网（V2X）数据流，融合前方道路状况、交通信号和周边车辆信息，实现更前瞻的驾驶安全预警。同时，基于长期积累的驾驶行为数据（分心频率、告警历史、偏好变化），构建个性化驾驶画像，为每位驾驶员提供定制化的交互策略和安全阈值。

\textbf{与当前设计的关系}：当前的边缘-云端混合架构和多Agent编排框架为上述演进提供了基础——SafetyAgent的VETO短路机制可直接适配V2X紧急事件，EvidenceAuditAgent的审计框架可扩展为V2X数据可信度校验，Agent记忆系统的三层架构可扩展为跨会话的个性化画像存储。
